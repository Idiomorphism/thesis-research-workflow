# 工作流程

## 1. 任务启动

1. 读取用户点名的 Skill、项目规则和目标文件。
2. 复述任务目标、允许修改的范围和禁止事项。
3. 区分“提出想法”“拟定文字”“在副本实施”“修改原文件”。
4. 检查目标材料是否齐全；能从项目发现的信息不重复询问。

## 2. 长项目读取

对整篇论文或大量对话，先建立清单，再分层阅读：

- 第一遍：文件、章节、时间线和任务类型盘点。
- 第二遍：用户纠正、否定、选择与最终认可，优先于助手自述。
- 第三遍：摘要、章首、章末、关键结果段和最终正文，用于验证实际风格。
- 第四遍：对冲突项回到原始对话或数据，不从单次表达推断稳定偏好。

蒸馏时区分三类信息：稳定原则、项目特定规则、一次性任务偏好。只有跨任务重复出现或被最终正文验证的内容，才进入核心 Skill。

## 3. 规划与执行分离

涉及章节重构、命名、研究设计、图表方案或高风险结论时，先给出计划和判断依据；用户要求“只说想法”时不得写入。获得授权后再执行，不把上一轮授权自动延续到新文件。

大幅修改时优先在用户指定副本中实施，或按其要求创建 `-1` 版本。不得覆盖原稿以换取便利。工作区已有未提交改动视为用户资产，只处理本任务相关部分。

## 4. 数据到论证

1. 核对数据来源、列名、单位、时间基准和工况映射。
2. 先获得描述统计、阶段特征和异常点，再设计图。
3. 图完成后检查遮挡、采样密度、图例顺序、色彩区分和轴范围。
4. 文字先陈述图中可见事实，再联合其他变量解释机制。
5. 把脚本、数据、图和正文中的数值逐项对照。

## 5. 研究章节修改顺序

推荐顺序：

1. 章的研究问题和作用。
2. 方法、假设与边界条件。
3. 数据/验证链是否完整。
4. 结果段的证据和机制。
5. 章末小结与全文主线衔接。
6. 语言、图表、排版和编译。

不要先润色一个结构或证据仍不闭合的章节。临近截止期时，优先关闭空章节、占位符、断裂引用、关键数据缺口和结论不一致，再处理美观。

## 6. 迭代协作

把用户的否定视为新的约束证据。收到“方向不对”后先停止当前路径，识别错误发生在目标、证据、结构还是措辞层，不在原方案上小修小补。用户承认指令不清并补充条件时，以最新的明确条件重建方案。

允许对用户指令提出批判性意见，尤其在以下情形：因果证据不足、验证外推过度、研究创新被流程替代、数据不可获得、文件操作范围不清或存在学术诚信风险。异议应附带可执行替代方案。

## 7. 交付

交付内容包括：完成结果、改动文件、验证结果、仍存在的限制。若只是诊断，不擅自实施修复。若用户请求可复用资产，同时交付说明性报告和机器可执行 Skill；报告解释形成了什么认识，Skill 约束后来者如何行动。
